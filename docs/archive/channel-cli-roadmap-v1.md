# channel-cli 발전 로드맵

**대상 저장소:** [Ted-Labs/channel-cli](https://github.com/Ted-Labs/channel-cli)  
**현재 버전:** 0.1.0 (Deprecated)  
**작성 기준:** 2026-10-30  

---

## 1. 현황 요약

channel-cli(Atrium 실행 구성요소)는 여러 채널(웹, Telegram 등)에서 들어온 요청을 **로컬 durable 큐**에 넣고, 워커가 꺼내 실제 AI CLI(`claude`, `codex`, `agy`, `opencode` 등)를 실행한 뒤 결과를 이벤트로 돌려주는 구조다.

### 현재 강점
- 외부 런타임 의존성 없음 (Python 3.11+, SQLite)
- `(channel, room, agent)` 단위 세션 분리
- `message-id` 기반 중복 방지
- `codex-body` 등 떠 있는 세션에 주입하는 body 모드
- 채널 연동을 위한 JSON/이벤트 계약이 명확함

### 현재 제약
| 항목 | 상태 |
|------|------|
| 동시성 | 전체 큐 FIFO, 워커 1개 (순차 처리) |
| 재시도 | 자동 재시도 없음. 수동 `retry`만 지원 |
| Body 모드 | `codex-body`는 interrupt/steer 지원, 나머지는 제한적 |
| 관측성 | 로그 파일 중심. 실시간 큐/실행 상태 조회가 약함 |
| 데이터 관리 | 자동 보존 기간·로그 정리 없음 |
| 확장성 | 어댑터가 코드에 고정, 플러그인 구조 없음 |

## 2. 개선 우선순위

### P0 — 체감 효과가 크고, 운영에 바로 도움 되는 것

#### 2.1 에이전트별 / 방별 병렬 처리
**문제**  
한 에이전트(예: `claude`)가 오래 걸리는 동안 다른 에이전트 요청까지 전부 대기한다.

**방향**
- 워커를 에이전트 단위로 분리하거나, `(agent)` 또는 `(agent, room)` 단위 concurrency limit 도입
- 설정 예시:
  ```text
  CHANNEL_CONCURRENCY_CLAUDE=1
  CHANNEL_CONCURRENCY_CODEX=2
  CHANNEL_CONCURRENCY_DEFAULT=1
  ```
- 전체 순차 모드도 유지 가능하도록 옵션화

**기대 효과**  
채널 응답 지연 감소, 여러 CLI를 동시에 활용하는 시나리오 가능

---

#### 2.2 실패 처리 강화 (retry + dead letter)
**문제**  
일시적 오류도 사람이 `retry`를 직접 해야 한다. 실패 원인이 로그에만 남아 운영 부담이 크다.

**방향**
- 시도 횟수(`max_attempts`)와 exponential backoff
- 재시도 가능한 오류 vs 영구 실패 구분
- 최종 실패 작업을 **dead letter** 상태로 분리
- `channel retry --all-failed`, `channel dlq` 같은 운영 명령

**기대 효과**  
일시 장애에 대한 복원력 향상, 수동 개입 감소

---

#### 2.3 Body 모드 기능 맞추기
**문제**  
`codex-body`는 interrupt/steer까지 있는데, `claude-body`·`agy-body`는 기능이 부족하다.

**방향**
- 실행 중 중단(interrupt)
- 실행 중 추가 지시(steer)
- 서버/데몬 재시작 후 세션 재연결
- body 모드별 공통 인터페이스 정리

**기대 효과**  
“이미 떠 있는 본체에 붙이는” 가치가 에이전트 전반으로 확장

---

#### 2.4 기본 관측성 (Observability)
**문제**  
큐 길이, 실행 중 작업, 소요 시간, 실패율을 한눈에 보기 어렵다.

**방향**
- `channel status` / `channel top` 명령 (현재 큐, running, 최근 실패)
- 작업별 소요 시간·시도 횟수 노출
- JSON 출력 유지 + 사람용 테이블 출력 병행
- (선택) 간단한 TUI 또는 로컬 웹 대시보드

**기대 효과**  
디버깅·운영 속도 향상

---

### P1 — 중기적으로 시스템을 단단하게 만드는 것

#### 2.5 우선순위·스케줄링
- `priority`, `delay`, `scheduled_at` 지원
- “사용자가 기다리는 요청”과 “백그라운드 작업” 구분
- 단순 FIFO를 기본으로 유지하고, 옵션으로 우선순위 큐 추가

#### 2.6 로그·데이터 정리 정책
- `CHANNEL_RETENTION_DAYS` 설정
- `channel gc` 명령 (완료/실패 작업, 오래된 로그 정리)
- 최소 보존 기간과 강제 삭제 옵션 분리

#### 2.7 어댑터 플러그인화
- 새 CLI 추가 시 코드 수정 없이 설정/플러그인으로 등록
- 공통 인터페이스: `detect`, `start_session`, `run`, `interrupt` 등
- 내장 어댑터(claude/codex/agy/opencode)는 기본 제공 유지

#### 2.8 선택적 세션 공유
- 기본은 에이전트 간 맥락 비공유 유지 (현재 설계 유지)
- 방 단위로 “공유 컨텍스트” 옵션 제공
- 멀티에이전트 협업 시나리오에만 명시적으로 사용

### P2 — 장기 발전 방향

| 항목 | 설명 | 난이도 |
|------|------|--------|
| 분산 모드 | 로컬 SQLite를 넘어 여러 머신 워커가 붙는 구조 | 높음 |
| 사용량·비용 고도화 | 에이전트/방/기간별 리포트 + 예산 한도 | 중간 |
| 채널 계약 강화 | at-least-once, 중복 처리 헬퍼, 재전송 가이드 | 중간 |
| 샌드박스·권한 | room/agent별 읽기전용·작업 디렉터리 제한 | 높음 |
| 결과 푸시 | 폴링뿐 아니라 웹훅으로 결과 전달 옵션 | 중간 |

## 3. 권장 진행 순서

실사용 기준으로 아래 순서를 권장한다.

1. **에이전트별 동시성 제어** — 체감 지연이 가장 먼저 줄어든다  
2. **재시도 + dead letter** — 운영 안정성  
3. **Body 모드 기능 맞추기** — 떠 있는 세션 활용 가치 확대  
4. **status / top 등 관측 명령** — 디버깅 비용 감소  
5. 우선순위·GC·플러그인화 — 규모가 커질 때

기능을 한꺼번에 늘리기보다, **실제로 아픈 지점부터** 푸는 것이 현재 아키텍처와 잘 맞는다.

---

## 4. 설계 시 유지할 원칙

현재 README에 드러난 설계 의도를 깨지 않는 선에서 발전시키는 것이 중요하다.

- **로컬 우선, 외부 의존성 최소화**  
- **에이전트 간 맥락 자동 공유 금지** (옵션으로만 허용)  
- **exactly-once를 과도하게 약속하지 않기** (부작용이 있는 CLI 실행 특성 인정)  
- **채널은 넣고(event) 읽고, 실행·세션은 CLI가 담당**하는 역할 분리 유지  
- JSON 계약과 사람용 CLI 출력을 모두 유지
